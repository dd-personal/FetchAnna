# Anna's Archive protocol notes

What FetchAnna relies on when talking to Anna's Archive and to SLUM, and how sure we are of each piece.

Every claim carries one of these labels:

- **LIVE**: observed over HTTP from a desktop on 2026-11-11, without an account key. Fixtures are in `spec/data/annas/` (see its `PROVENANCE.md`).
- **SOURCE**: read in Anna's public source code at `https://software.annas-archive.gl/AnnaArchivist/annas-archive`, commit `a15b123c9c2e7e5919a0ad2440b2cc5649ebd8aa` (main, 2026-11-04). The deployed sites may differ from this commit.
- **UNVERIFIED**: inferred, or needs a real member key to confirm. Nothing labelled this way may be presented to users as fact.

## 1. Origins and roles

SLUM (`https://open-slum.org/annas.html`) lists six hosts for Anna's Archive, in three roles that must not be mixed up. **LIVE**

| Host | SLUM id | Role | SLUM status 2026-11-11 | What SLUM expects |
| --- | --- | --- | --- | --- |
| `annas-archive.gl` | `annas.gl` | Catalogue and account | PROTECTED (DDoS-Guard) | 200, text "in one place - Anna" |
| `annas-archive.pk` | `annas.pk` | Catalogue and account | PROTECTED (DDoS-Guard) | same |
| `annas-archive.gd` | `annas.gd` | Catalogue and account | PROTECTED (DDoS-Guard) | same |
| `software.annas-archive.gl` | `annas.software` | Source code (GitLab) | PROTECTED (DDoS-Guard) | 200, text "AnnaArchivist" |
| `yqrii5.org` | `annas.dl1` | Download server | UP | 403, text "Link expired or invalid" |
| `wbsg8v.xyz` | `annas.dl2` | Download server | UP | 403, text "Link expired or invalid" |

- PROTECTED means only that a bot challenge answered, not that the site works. SLUM skips its content check for these.
- On a download server, a 403 "Link expired or invalid" is the expected healthy answer to a bare request. It is a health signal, not a file.
- The source lists more download servers than SLUM monitors: `wtgadtq.org`, `b4mcx2ml.net` and one configured by environment variable, besides the two above. **SOURCE** Download servers are therefore learned from the API's answers, never from a fixed list.

### SLUM page structure **LIVE**

- No machine-readable feed: `/api.json`, `/annas.json`, `/status.json` and `/feed.json` all return 404.
- Each host is a `<div class="card" id="annas.gl">` with a title link `<a href="https://annas-archive.gl" class="card-title">` and a status badge `<span class="status-badge protected">PROTECTED</span>`.
- Each card's logs button has `data-domain-id`, `data-domain-url` (the bare host) and `data-log-path` (for example `logs/annas/gl.log`). These logs are CSV with a `# version: 2` header line; columns 0, 3, 4, 5 and 6 are timestamp, status, HTTP status, latency (ms) and failure reason.
- Roles are not marked up. They can be told apart by:
  - each card's expected content (`"in one place - Anna"`, `"AnnaArchivist"`, `"Link expired or invalid"`)
  - the `dlN` and `software` ids
  - a prose note under the cards that names the download hosts

  The parser should use the expected-content field first and the id second. A card it can't classify is left out.
- The page is generated by FlatMonitor (`github.com/BrianZbr/flatmonitor`) and served through Cloudflare. Its footer gives the generation time, which can be used to measure how stale the data is.

## 2. Bot protection and member access

### What happens without a session **LIVE**

| Request | Answer |
| --- | --- |
| `GET /faq` | 200, full page, no challenge |
| `GET /dyn/api/fast_download.json` | JSON (400 or 401), no challenge |
| `GET /search?q=…` | 302 to the same URL plus `&check=1` (Anna's own Flask redirect, not DDoS-Guard) |
| `GET /md5/<md5>` | 302 to `/md5/<md5>?&check=1` |
| `GET` of any `&check=1` URL | 403 DDoS-Guard JavaScript challenge, titled `DDoS-Guard`, loading `check.ddos-guard.net/check.js`, with the text "Checking your browser before accessing" |

All three catalogue hosts behaved identically, and every response carried `Server: ddos-guard`.

### How the gate works **SOURCE**

- Search, record (`/md5/…`), codes and SciDB pages are **member-protected**.
- Before serving one of these pages, the app looks for a logged-in account (the `aa_account_id2` cookie) with a current membership whose tier allows skipping browser checks.
  - If it finds one, the page is served directly.
  - Otherwise the visitor is redirected to `&check=1`, where DDoS-Guard challenges them.
- A member can skip checks only up to an hourly allowance per page type. Past that allowance they are sent to the challenge too. The allowance is a base figure times the tier's factor:

  | Page type | Base allowance per hour |
  | --- | --- |
  | Search | 180 |
  | Record (`/md5/…`) | 600 |
  | Codes | 180 |
  | SciDB | 60 |

- Tier factors and daily fast downloads:

  | Tier | Skip-check factor | Searches per hour | Fast downloads per day |
  | --- | --- | --- | --- |
  | 1 | 0 | none (always challenged) | 0 |
  | 2 | 0.2 | 36 | 25 |
  | 3 | 1 | 180 | 50 |
  | 4 | 1 | 180 | 200 |
  | 5 | 1 | 180 | 1000 |

  Bonus downloads can raise the daily figure. An account doing fewer than 450 downloads a day counts them over an 18-hour window instead of 24.

### History

KindleFetch, which FetchAnna is forked from, searched Anna's Archive's `/search?…&display=table` pages until v0.3. In August 2026 its users reported that searches returned "No books found" ([KindleFetch issue 24](https://github.com/william-spongberg/KindleFetch.koplugin/issues/24)). KindleFetch then switched to Library Genesis (`c073e95`, 2026-09-28). That matches the member gate above: the challenge page was read as an empty list of results. This is why FetchAnna reports any page it can't recognise as a parser error or a bot check, never as "no books found".

### Consequence for FetchAnna

Native search and detail pages are only possible as a **logged-in member whose tier skips browser checks**. This is Anna's own member feature, not a way around the challenge. Anonymous users, tier-1 members and members over their hourly allowance get the challenge, which FetchAnna must report as such ("needs a browser check") and never try to solve. **UNVERIFIED**: whether DDoS-Guard itself challenges a member's session from KOReader's HTTP clients before the request reaches Anna's app. Our anonymous first requests were passed through to the app, which suggests it doesn't, but that needs a member test.

## 3. Account and session

### The secret key **SOURCE**

- The secret key is the account's 7-character id followed by a base58 MAC that only the server can compute.
- Keys shorter than 20 characters are rejected outright.
- The key is the only credential an account has. No email or password is involved.

### Logging in **SOURCE, then LIVE**

- `POST /account/` with form field `key=<secret key>` (`application/x-www-form-urlencoded`).
- Valid key, active account:
  - 302 to `/account/`
  - `Set-Cookie: aa_account_id2=<JWT without its prefix>`, `HttpOnly`, `SameSite=Lax`, `Secure` on HTTPS hosts, 90-day expiry
  - The cookie's `Domain` is the site's base domain, so a session made on `annas-archive.pk` is sent only to `*.annas-archive.pk`.
- Invalid key: 200 with the account page, which shows an invalid-key message. No cookie is set.
- Logging in records the account id and client IP on the server.
- **LIVE** (2026-11-11, a Kindle Paperwhite 5 SE fetching with curl 8.21.0): `POST /account/` on `annas-archive.gd` reached the app without a challenge and gave a session, and the account page read with it showed the membership (tier 2). See `docs/account.md`.

### Logging out **SOURCE**

- `PUT /dyn/account/logout/` with the session cookie answers `{"aa_logged_in": 0}` and clears the cookie.
- Without the cookie it errors, so the plugin should simply discard the cookie locally whatever the answer.

### Checking a key without spending a download **SOURCE**

`/dyn/api/fast_download.json` checks things in this order:

1. MD5 format (400 "Invalid md5")
2. Key (401 "Invalid secret key")
3. Whether the record exists (500 "Error during fetching", 404 "Record not found")
4. Membership (403 "Not a member")
5. Path and server indexes (400 "Invalid domain_index or path_index")
6. Quota (429 "No downloads left")

So asking for a correctly formed MD5 that matches no record tells a valid key (404) from an invalid one (401) without touching the quota. It says nothing about membership. That is learned at login (whether search is served), or on the first real download.

**UNVERIFIED**: whether an all-zero MD5 is guaranteed to match no record. Using a random 32-hex value is safer.

## 4. Fast-download API

The API documents itself in every response. **LIVE + SOURCE**

`GET /dyn/api/fast_download.json?md5=<md5>&key=<secret key>[&path_index=<n>][&domain_index=<n>]`

- `md5`: required, 32 lowercase hex characters. Uppercase, padding or extra characters are rejected.
- `key`: required, the secret key, **in the query string**.
- `path_index`: optional, default 0. Which collection's copy of the file, when there is more than one.
- `domain_index`: optional, default 0. Which download server.
- No session cookie is needed.
- The response is JSON with `Content-Type: text/json; charset=utf-8` and `Cache-Control: no-cache`.

| Status | `error` | Meaning |
| --- | --- | --- |
| 200 | absent | `download_url` is set, along with `account_fast_download_info` (`downloads_left`, `downloads_per_day`, `downloads_done_today`, `recently_downloaded_md5s`). The docs also mention 204. |
| 400 | `Invalid md5` | |
| 400 | `Invalid domain_index or path_index` | |
| 401 | `Invalid secret key` | |
| 403 | `Not a member` | No current membership. |
| 404 | `Record not found` | |
| 429 | `No downloads left` | |
| 500 | `Error during fetching` | Search backend failure. Safe to retry later. |

Every response also carries a `///download_url` array of documentation lines, which the parser ignores.

### Quota

- A successful call for an MD5 **not** in `recently_downloaded_md5s` records a download, which counts against the quota.
- Calling again for an MD5 that **is** in that list costs nothing.
- So refreshing an expired link for the same book is free. Trying a different book is not.
- A call that timed out may already have been counted. Before calling again, check whether the book is now in `recently_downloaded_md5s`, which a later response reports.

### The download URL

- It is `https://<download server>/<signed path>`.
- The path carries the account id, an expiry **two hours** after it was issued, a speed limit and a hash.
- It is a bearer credential: anyone holding it can download the file until it expires.
- Changing its host invalidates it, so to switch servers, ask the API again with another `domain_index`.
- Accounts past 600 downloads in the window, and again past 1200, are given slower server lists.

**UNVERIFIED**: the served file's `Content-Type`, `Content-Length`, whether `Range` requests work, and redirects. All need one authorized test download of a public-domain book.

## 5. Search **SOURCE, then LIVE**

`GET /search` with these query parameters. Anything not listed is ignored. **SOURCE**

| Parameter | Meaning |
| --- | --- |
| `q` | The query, UTF-8, URL-encoded. |
| `lang` | Language code. Repeatable, for example `lang=en&lang=de`. |
| `ext` | File extension. Repeatable, for example `ext=epub`. |
| `content` | Content type. Repeatable. |
| `acc` | Access type. Repeatable. |
| `src` | Record source. Repeatable. |
| `sort` | Sort order. Empty means relevance. |
| `desc` | `1` for descending. |
| `page` | 1 to 100, clamped to that range. |
| `display` | Result layout. Empty is the list view, which FetchAnna reads. |
| `index` | Which search index. Empty means the default book index. |
| `termtype_<n>`, `termval_<n>` | Advanced field-scoped terms (title, author, ISBN and so on). Not offered, as not checked live. |

FetchAnna sends `q`, then `lang` for each language chosen (none when every language is, meaning any), then `ext` for each file type chosen (only those KOReader opens), then `page` after the first. It sends the session cookie for that exact site, and doesn't follow redirects.

**LIVE** (2026-11-13, the owner's tier 2 account on a Kindle Paperwhite 5 SE): searching from FetchAnna returned epub results whose titles, authors, years, languages, kinds, sizes and covers read correctly.

### What a page of results looks like **LIVE**

Checked on a member's (tier 2) page, saved from a browser on 2026-11-11 (`spec/data/annas/search-results-member.html`), against Anna's template (`allthethings/templates/macros/aarecord_list.html` at `a15b123c`). The template renders the same markup as the saved page, but with relative links and no results hidden in comments.

- 50 results per page, at most 100 pages.
- The page's own results are in the **first** `div.js-aarecord-list-outer`. A second one holds "partial matches" behind a hidden button, and a bar above both lists the whole site's recent downloads. Only the first list is read.
- Each result starts with a link to `/md5/<md5>`, so the MD5 is the file's identity. Each result is read as the stretch of the list from its first `/md5/` link to the next result's:

  | Field | Where it is |
  | --- | --- |
  | Title | The link with the `js-vim-focus` class, which the page itself uses to step between results. |
  | Author | The link with an `icon-[mdi--user-edit]` icon. |
  | Publisher and edition | The link with an `icon-[mdi--company]` icon. |
  | Original file name | The `font-mono` line. |
  | Cover | The first `<img>`. |
  | Details | One line (`div.text-gray-800…`): language name and `[code]`, file type in capitals, size rounded (`0.6MB`), year, kind (`📕 Book (fiction)`), then the collections holding it (`🚀/lgli/zlib`), separated by ` · `. Any of these can be missing. |

  The size is only ever kept as Anna's rounded label, never as a byte count.
- **The next page** is the `a.js-pagination-next-page` link, whose `page=` must be higher than the current page and at most 100. Without that link, it's the last page.
- **No results** is still the search page with an empty list.
- **Timeouts:**
  - Anna's search timing out with no results puts a ❌ warning (a literal emoji in the template, so the same in every language) above the empty list.
  - A fatal timeout leaves the list out altogether.

  Both are reported as Anna's Archive answering with an error, never as "no books".

### When a member can't search **SOURCE**

A browser check (the `&check=1` redirect, or DDoS-Guard's page) is the account's doing, not the site's. It happens when the tier doesn't skip checks, or this hour's allowance is used up, and each such request counts against that allowance too. So FetchAnna stops at the first one rather than trying the other sites. The one exception: a session over an hour old may simply no longer be taken, so FetchAnna logs in on that site again and asks once more.

The search then says so, with a **Search in a Browser** button. It shows the same search's address on one of Anna's sites, and a QR code of it where KOReader has its QR widget, to open on a phone, whose browser can do the check. Typing the link or MD5 of a book found that way into the search box downloads it through the member API (see [downloads.md](downloads.md)).

### Why not just "no books" **LIVE**

KindleFetch's Anna's Archive search broke in August 2026 exactly this way (see the History in section 2). FetchAnna reports:

- an unrecognized page as unreadable ("its pages may have changed")
- a bot check as such
- a timeout as an error

Only a recognized results page with an empty list means none were found.

Other public JSON, served without a challenge (**SOURCE**, not used yet):

- `/dyn/search_counts?q=…`: hit counts per index.
- `/dyn/md5/inline_info/<md5>`: counts of reports and comments.
- `/dyn/api/aarecord_elasticsearch/<id>.json?key=…`: full record metadata, but only for accounts with a separate `special_apis` flag, so it isn't a general search API.

## 6. What must not leave the device, or go to the wrong host

- The **secret key** goes only to trusted catalogue origins over HTTPS:
  - in the `POST /account/` form body, and
  - in the `key` query parameter of `/dyn/api/fast_download.json`.

  Every URL carrying it must be redacted as a whole, kept off curl's command line, and never written to logs, diagnostics or caches.
- The **session cookie** (`aa_account_id2`) goes only to the exact origin that set it.
- **Signed download URLs** are credentials for two hours. They must be redacted the same way, kept off command lines, and never cached across sessions.
- None of the above, nor any credential-bearing `Referer`, goes to SLUM, cover hosts, the software host, or download servers. Download servers get only their own signed URL.
